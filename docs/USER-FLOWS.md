# InsightForge 用户流程

- 版本：`DRAFT v1.2`
- 状态：`待原型验证`
- 设计原则：三个核心场景优先；正常路径、失败路径和责任边界同等重要。

## 1. 角色

- 研究执行者：发起任务、查看过程、处理候选、导出成果。
- 判断负责人：追问依据、确认/编辑/驳回结论、处理争议。
- 现场评委：在五分钟内观察产品价值，不是独立业务角色。

本期为单用户、单会话，不实现身份、权限或多人协作。

## 2. UF-01 黄金主流程：问题到成果

### 触发

用户打开工作台，看到默认黄金问题和明确的“使用缓存快照”标签，点击唯一主按钮“运行黄金案例”。

### 正常路径

1. 系统创建任务并立即显示五状态。
2. `PLAN` 在离线模式加载并校验缓存模型计划；在线模式才生成结构化范围、步骤与工具映射。
3. `COLLECT` 读取搜索快照、PDF 页和 CSV/XLSX，形成 Source/Evidence/Datum。
4. `SYNTHESIZE` 读取结构化证据；离线模式加载并校验缓存模型候选，在线模式生成 3–5 条模型候选。
5. `AUDIT` 检查六类问题，最多执行一次真实修正或降级。
6. `DELIVER` 从同一运行对象生成交互报告、PPTX 与 JSON。
7. 页面显示 `DELIVERED` 或 `NEEDS_REVIEW`，不把未解决严重问题显示为成功。

### 页面反馈

- 每步显示 `pending/running/success/failed`，至少能真实观察一次 `running`。
- 默认只显示用户能理解的产物摘要；工具事件可展开核验。
- 刷新后恢复当前任务和成果。

### 失败路径

- 任一步失败：后续步骤停止，终态为 `FAILED`，显示安全错误和可重试入口。
- 模型/快照输出 Schema、引用或问题不匹配：`SYNTHESIZE` 失败或进入明确的 fail-closed 结果，不静默使用固定结论。
- Audit 一次修复后仍有严重问题：终态 `NEEDS_REVIEW`。

## 3. UF-02 结论追溯与人工判断

### 触发

用户在“研究报告”中点击任一候选结论。

### 正常路径

1. 一次点击打开证据抽屉。
2. 有支撑的候选按 `Conclusion → Claim → Evidence/Datum → Source → Locator` 展示；估算/预测同时展示 Assumption。
3. 证据不足候选展示 `Conclusion → Claim → EvidenceGap`，列出已有部分材料、缺少的来源/指标/口径和不可确认原因，不伪造 Source。
4. 用户查看来源摘录、PDF 页码、表格行/单元格或计算公式。
5. 用户返回结论卡并选择确认、驳回或编辑。
6. 系统记录决定时间、确认后文本和原始模型文本；冲突、估算或预测还记录决定理由和适用范围。
7. 系统生成新的成果版本；旧成果和旧决定保留。

### 状态规则

- `PENDING_REVIEW + SUPPORTED/CONFLICT`：允许确认、驳回、编辑。
- `INSUFFICIENT_EVIDENCE`：只允许查看依据、驳回或保留待处理；禁止确认。
- `STALE`：禁止确认，必须重新运行或复核。
- 人工编辑不是改写历史；原模型版本必须保留。

### 冲突路径

同一指标的不同值同时显示来源、口径和时间。系统可给出“候选解释”，但不静默择一、不求平均，也不把解释标为事实。

## 4. UF-03 场景二的系统子流程：Audit→Repair

该流程没有独立一级入口，不构成第四个产品场景。

### 触发

候选结论生成后自动进入 Audit。

### 正常路径

1. Audit 消费本轮结构化 Evidence、Datum、Claim、Conclusion。
2. 输出类别、严重度、目标、原因和动作。
3. 对一个可自动修复问题执行结构归一、挂接已存在假设、降级、标冲突或阻断；程序不得凭空补假设或语义改写。
4. 页面同时展示 before/after 与修复次数 `1/1`。
5. 未解决问题进入人工处理列表。

需要新增假设或改写文本时，模型或用户产生新候选版本，重新 Audit，且保持 `PENDING_REVIEW`。

### 反证路径

如果同一结论补入真实支撑证据，Audit 结果必须改变；如果移除引用或伪造 ID，Audit 必须重新发现问题。固定对象 ID 驱动的剧本不合格。

## 5. UF-04 来源更新与失效

### 前置

用户已确认至少一条受来源 A v1 支撑的结论，同时有一条不依赖来源 A 的结论。
缓存模型与在线单端点模型运行使用同一后端更新合同；模型生成的动态 Claim/Conclusion ID 不得使该路径退化为只读说明。

### 正常路径

1. 用户点击“发现新版来源”，按钮旁持续显示“载入内置 v2 演示快照”。
2. 系统显示 v1→v2 的 Datum 差异。
3. 系统列出受影响 Evidence、Datum、Claim、Conclusion 和成果。
4. 受影响 Claim 变为 `STALE`，Conclusion 变为 `NEEDS_REVIEW`。
5. 相关人工决定保留原记录并增加失效时间、原因和 updateId；不相关结论保持不变。
6. 用户点击“重新计算并更新成果”。
7. 系统展示前后差异及新 PPTX/JSON ArtifactVersion；旧版本仍可审计。
8. 页面刷新或后端重启后，v2、受影响对象、失效决定和新 ArtifactVersion 均从后端恢复；前端不维护独立副本。

### 失败路径

- v2 无法解析：保留 v1 和原成果，显示更新失败，不制造部分新状态。
- 影响链不完整：进入 `NEEDS_REVIEW`，不得声称更新完成。

## 6. UF-05 本地资料摄取

### 产品边界

资料摄取是次要能力，只有在文件被解析、建模并通过 Audit 后才可成为证据。若本期只完成安全上传，入口必须写“验证并保存资料”，不能写“加入研究”。

### 流程

1. 用户选择 PDF/CSV/XLSX/TXT，页面显示 5 MiB 限制。
2. 浏览器和服务端执行类型、字节、大小、名称和目录校验。
3. POST、磁盘 GET 和浏览器本地 SHA-256 一致后才显示保存成功。
4. 页面明确显示 `已保存，尚未进入证据链`。

### 拒绝路径

伪装格式、超限、路径穿越、NUL/非法 UTF-8、异常 XLSX、哈希篡改全部 fail-closed；错误不暴露服务器路径、环境变量或凭据。

## 7. UF-06 折叠边界验证：非黄金问题 fail-closed

1. 用户展开“边界验证”，把研究问题改为与内置资料无关的问题；主流程默认黄金问题不变。
2. 主按钮改为“检查当前资料是否匹配”，不暗示能完成第二行业研究。
3. PLAN 的范围和待收集信息随问题实质变化。
4. 系统不得输出新能源乘用车或充电设施的预写结论。
5. 在没有匹配资料时，输出至少三条问题相关的 `INSUFFICIENT_EVIDENCE` 候选，分别说明缺少的信源、指标、口径或交叉验证。
6. 不允许确认；产品解释当前离线案例边界。

该流程是泛化反证，不是第二个行业交付案例。

## 8. UF-07 离线与在线模式

- 默认黄金模式：`sourceDiscoveryMode=OFFLINE_SNAPSHOT`、`authorityVerificationMode=NOT_RUN`、`synthesisMode=CACHED_MODEL_OUTPUT`，执行“加载、解析、计算、校验、审查和交付”，可断网运行。
- 用户展开“在线能力验证”后，分别选择来源发现、白名单核验或候选生成；三项没有一个混合总开关。
- 在线信源发现：`sourceDiscoveryMode=LIVE_SINGLE_PROVIDER`，只调用一个允许的搜索提供方，显示查询、提供方和失败状态；结果未解析/建模前不是证据。
- 固定白名单来源核验：`authorityVerificationMode=LIVE_ALLOWLIST`，只验证当前权威页面，不等于在线搜索，也不改变来源发现模式。
- 在线候选生成：`synthesisMode=LIVE_SINGLE_ENDPOINT`。端点由部署者在服务端安全预配置，页面只显示配置状态与模式，不接收 API Key；失败即失败，不自动切换或回退为缓存。
- 非黄金问题失配时使用 `synthesisMode=DETERMINISTIC_MISMATCH_BLOCK`，不能冒充模型调用。

三个模式字段必须在任务顶部、结果对象和导出中逐项一致显示；未执行的能力明确写 `NOT_RUN`，不能借另一项成功声称“在线已验证”。

## 9. 可用性验收任务

每位测试参与者独立完成：

1. 发起黄金任务，并指出当前运行到哪一步。
2. 找到指定结论的原始依据并说出定位。
3. 解释两个冲突数字为何不能直接合并。
4. 判断哪条结论不能确认，并说明原因。
5. 编辑或确认一条支持充分的结论。
6. 切换来源 v2，并指出受影响和未受影响的结论。
7. 下载 PPTX 和证据 JSON。
