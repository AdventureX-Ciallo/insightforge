# InsightForge 最小化产品策略

- 版本：`DRAFT v1.1`
- 状态：`待产品文档冻结`
- 目标：用一个行业案例、三个核心场景和一条五分钟叙事，同时证明两个赛题命题。

## 1. 产品定义

本策略直接依据两份官方命题及项目所有者解释；逐条证据见 `docs/BRIEF-RESEARCH-EVIDENCE.md`。它们是本次黑客松的首要产品调研证据，不以额外用户问卷作为立项前提。

### TL;DR

InsightForge 是面向行业研究者的证据工作台：它接住一个研究问题，调用搜索、文件、计算和 PPTX 工具，把候选判断交给规则审查与人工确认，并交付可以继续编辑、可以追到底稿、可以随来源变化更新的成果。

### 核心承诺

`从一个行业问题，到一份能下钻、能质疑、能更新的研究成果。`

### 两个命题如何统一

- 商汤小浣熊定义纵向任务链：从需求到计划、工具、执行校验和成果。
- 沙利文定义这条链的质量合同：证据可见、判断可质疑、变化可追踪、人对结论负责。
- 产品只讲一个故事：`完整推进一次有证据责任的行业研究任务`。

## 2. 三个最小核心场景

### 场景一：把整个任务接到成果

用户输入研究问题并启动任务。产品自然推进 `PLAN → COLLECT → SYNTHESIZE → AUDIT → DELIVER`，真实消费搜索快照、PDF、CSV/XLSX 计算与 PPTX 工具输出，最终交付交互报告、可编辑 PPTX 和证据 JSON。

评委应立即看见：这不是聊天，也不是四个孤立按钮。

### 场景二：追问一条结论

用户点击任意候选结论，在最多两次操作内看到 Claim、Evidence/Datum、Assumption、Source 和精确 locator；同一主题的两个不同口径值并存，一条合理但证据不足的判断展示 EvidenceGap 并被阻止确认。用户可以确认、驳回或编辑有充分证据的候选。

评委应立即看见：系统的差异不是“结论更多”，而是“知道依据和边界”。

### 场景三：新来源让旧判断失效

用户点击“发现新版来源”，同时明确看到“载入内置 v2 演示快照”。产品列出受影响数据、Claim、Conclusion 与成果；旧人工决定保留但标记失效，重新计算并生成新 PPTX/JSON 版本；无关结论保持不变。

评委应立即看见：研究成果不是静态终稿，而是可维护的判断系统。

## 3. 能力与场景的关系

| 能力 | 服务场景 | 是否独立卖点 |
|---|---|---|
| 五状态与事件日志 | 场景一 | 否，是任务可信度证明 |
| 四类真实工具 | 场景一 | 否，是完整任务链的执行基础 |
| 模型提出、程序校验 | 场景一、二 | 是，核心责任边界 |
| 研究对象、证据/缺口路径与正交状态 | 场景二 | 是，第一高光的内核 |
| Audit→Repair 一次闭环 | 场景二 | 是，但必须由输入驱动 |
| 人工确认/编辑/驳回 | 场景二 | 是，最终判断责任 |
| 来源 v1/v2 影响链 | 场景三 | 是，第二高光的内核 |
| 上传与实时核验 | 输入保障 | 否；没有进入研究链前不得占据主流程 |
| 离线快照 | 现场稳定 | 否；必须显式标记 |

## 4. 黄金任务

唯一交付案例：`中国新能源乘用车渗透率增长与公共充电基础设施之间，存在哪些约束迹象与证据边界？`

该案例必须自然包含：

- 可核对的公开来源、一个明确标记的带页码合成演示 PDF、一个 CSV 计算输入；XLSX 仅作为允许输入/上传类型验收，不是黄金任务必需；
- 至少三条候选判断；
- 一个范围或口径冲突；
- 一个确定性公式计算和一个带假设估算；
- 一个证据不足结论；
- 一次由真实输入触发的 Audit 修正或降级；
- 一次人工决定；
- 一次来源更新失效；
- 三个真实成果。

更换问题只用于 fail-closed 泛化验收，不构成第二个交付案例。

## 5. 72 小时切线

### 必须保留

- 三个核心场景完整、自然、可从用户入口运行。
- 五状态与四类工具确实消费前一步产物。
- 100% 结论具有支持路径或证据缺口记录；支持路径引用均可定位；0 条证据不足结论被确认。
- 模型候选、确定性审查与人工确认三者来源可区分。
- 离线黄金路径、可编辑 PPTX 和 JSON 证据包。

### 可以降为次要入口

- 任意文件的安全摄取；若未进入证据链，必须标记为实验性输入能力。
- 固定白名单实时来源核验；网络失败不影响黄金任务。
- 工具事件的完整技术字段；默认折叠，仅在核验时展开。

### 直接删除或禁止进入主流程

- 通用聊天入口和自由工具面板。
- 第二行业案例、多个模板、多个模型、自动监控。
- 与三场景无直接关系的账户、协作、知识库与设置页面。
- 只为匹配清单而存在、用户无法理解价值的独立按钮。

## 6. 允许的人工与缓存边界

为保证黑客松稳定，可以：

- 人工选择并固化唯一黄金案例的公开资料快照。
- 保存一次真实模型生成且通过 Schema 校验的离线候选快照。
- 提供已生成 PPTX 作为灾备。

但必须：

- 在 UI、JSON 和路演中标记“缓存搜索快照”“缓存模型输出”，离线步骤使用“加载并校验”措辞。
- 现场仍真实执行解析、计算、审查、更新和成果生成。
- 不把开发者手写固定结论标为 AI 输出。
- 不把灾备文件或预录视频称为现场运行。

## 7. 产品边界应由界面表达

借鉴“容器即心智”，本产品不依赖小字警告表达责任：

- `候选判断` 区只出现 AI 结果，默认待审。
- `人工确认` 是显式动作，并显示确认后文本与时间。
- `证据不足/冲突/过期` 使用独立状态和不可确认交互。
- `缓存快照/实时调用` 在任务顶部持续可见。
- 未进入研究链的上传文件放在“资料摄取”次要区，不与已采用证据混排。
- 首次 DELIVER、人工决定和来源更新分别生成可追踪成果版本；旧版本与旧决定不删除。

## 8. MVP 成功指标

### 产品可理解性

- 4/5 目标用户能用一句话说出产品不是聊天机器人。
- 4/5 能独立找到任一结论的原始依据，且不超过两次操作。
- 4/5 能正确解释知识类型、`AI_JUDGMENT` 和 `HUMAN_CONFIRMED` 属于不同责任/审阅轴。
- 4/5 能指出来源更新后哪条结论需要复核、哪条不受影响。

### 工程与现场

- 十二条 P0 全部通过，任何一条失败都不称 MVP 完成。
- 干净环境可安装、测试、构建、启动。
- 黄金链连续运行三次成功，单次不超过三分钟，目标 90 秒内。
- 五分钟内完整讲完三个场景。
- 路演用黄金任务目标 ≤50 秒；P0 稳定性上限仍为 3 分钟，两者分别验收。

### 不采用的虚荣指标

不以页面数、Agent 数、模型数、来源数量、代码行数或报告篇幅作为成功标准。

## 9. MVP 失败条件

出现任一项即回到产品或范围评审：

- 用户认为这是一个带报告模板的聊天机器人。
- 用户无法从结论找到依据，或看不懂冲突/不足状态。
- 改问题后仍套用黄金案例结论。
- Audit 对输入变化无反应，或修复无限循环。
- 上传入口暗示文件已用于研究，但实际上没有进入证据链。
- 离线快照被误认或宣传为实时搜索/实时模型调用。
