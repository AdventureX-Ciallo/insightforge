# “你好，小刘 · Hiliu”产品方法拆解与复用

- 版本：`DRAFT v1.0`
- 参考项目：[知乎黑客松项目页](https://www.zhihu.com/hackathon/project/10?activity_code=zhihu_hackathon_2026_p1)
- 参考附件：项目页链接的 34 页《你好，小刘》产品说明 PDF
- 用途：借鉴做产品与最小化表达的方法，不复制其产品、数据或技术范围。

## 1. 它的“全套思路”是什么

参考项目的完整性不在于功能多，而在于证据链完整：

```text
真实问题
→ 开发前调研
→ 一句话定位
→ 三个核心场景
→ 产品边界由容器表达
→ 技术只解释场景内核
→ 可下载产品
→ 真实使用反馈
→ 正负证据推动迭代
```

## 2. 公开材料中的关键做法

### 2.1 先让人十秒看懂

项目页先给 TL;DR：它是什么、谁住在里面、与知乎如何绑定。读者无需先看架构就能判断产品是否有独特价值。

对应启发：InsightForge 先说“从一个行业问题，到一份能下钻、能质疑、能更新的研究成果”，不能先讲状态机、Zod 或 PDF.js。

### 2.2 先证明问题，再提出方案

项目公开了一次 123 人的开发前调研，样本画像、痛点、期待和桌宠兴趣均有原始脱敏数据链接。核心不是数字多，而是问题与方案形成闭环：用户嫌切换页面，期待随时唤起，因此选择桌面常驻形态。

对应启发：InsightForge 的立项证据来自两份官方命题。我们可以证明“这是赛题要求解决的问题”，但没有自己的用户调研时，不能借用 Hiliu 的数字或声称市场已验证。

### 2.3 用一句朴素目标约束功能

Hiliu 的目标是“把知乎请到桌面上来”，比“通用 AI 桌宠平台”更具体。后续场景、界面和接口都能回到这句话。

对应启发：InsightForge 只解决“一次有证据责任的行业研究任务”，不扩展成通用 Agent 平台或知识图谱。

### 2.4 只讲三个核心场景

项目页没有把所有 API 和按钮列成卖点，而是讲：叼热榜、知乎来找你答题、答案回来找你。三个场景分别有触发、动作、结果和独特价值。

对应启发：InsightForge 只讲接住任务、追问结论、跟踪变化；上传、实时核验、Schema 和事件日志都是支撑能力。

### 2.5 让容器本身表达规则

Hiliu 用“容器即心智”区分私密对话和公开答题：桌宠气泡永远私密，独立答题窗才是公开内容。边界不是一行用户会忽略的警告。

对应启发：

- AI 候选区不能看起来像最终报告。
- 人工确认必须是显式动作。
- 证据不足和过期内容不能拥有可用的确认按钮。
- 缓存模式要持续显示，不藏在设置或脚注。
- 未入证据链的上传文件不能与 adopted evidence 混排。

### 2.6 做出产品后再次验证

项目又收集了 31 名实际使用者反馈，既展示高频使用和推荐意愿，也公开免打扰、代码复制等负面反馈。它证明团队不是只用开发前问卷给想法背书。

对应启发：InsightForge 至少应做命题适配验证和五项任务可用性测试；如果没有用户测试，如实写“尚未执行”，不能制造成功故事。

### 2.7 技术只选与场景直接相关的部分

项目页最终只重点解释三类技术：模型协议统一、能力画像萃取、双向语义匹配。34 页说明书可以很技术，但公开叙事只选支撑核心场景的内核。

对应启发：InsightForge 路演只讲五状态与工具事件、证据合同与输入驱动 Audit、来源依赖与成果再生成三根支柱。

### 2.8 给出真实体验入口和持续更新

项目提供公开下载、版本更新、GitHub/产品链接、截图、用户数据和评论。产品价值最终由可体验结果承担，不由设计稿或技术报告承担。

对应启发：InsightForge 最终应从干净环境运行并真实生成成果；灾备 PPTX 和预录视频不能替代现场任务链。公开仓库、Tag 和部署仍需项目所有者授权。

## 3. 转译到 InsightForge

| Hiliu 方法 | InsightForge 最小做法 |
|---|---|
| TL;DR 三问 | 一句话定位 + 目标用户任务 + 双命题连接 |
| 123 人开发前调研 | 两份官方命题作为立项证据；用户/市场假设另列 |
| “把知乎请到桌面” | “把一个行业问题推进为可追问成果” |
| 三个核心场景 | 接住任务 / 追问结论 / 跟踪变化 |
| 容器即心智 | AI/人、缓存/实时、上传/证据的可见边界 |
| 31 名实际用户回访 | 命题适配 + 目标用户任务测试 + 正负反馈 |
| 三项关键工程 | 状态工具链 / 证据 Audit / 变化与再交付 |
| 可下载产品 | 干净环境、可编辑 PPTX、JSON、真实演示视频 |

## 4. 不复用的部分

- 桌宠、人格化 IP、桌面常驻、主动推送。
- 知乎 API、社区内容回灌和答案匹配。
- 多模型协议统一、故障转移、向量语义重排。
- 长期记忆、用户画像、后台持续匹配。
- 参考项目的用户数字、商业前景和技术结论。

这些内容要么与命题无关，要么被本项目禁止，要么无法在 72 小时内可靠验证。

## 5. 对当前项目流程的直接纠正

参考方法暴露出首轮原型的过程问题：

1. P0 清单不是完整产品逻辑；需要先把它们组织成三个场景。
2. 架构与测试不能替代产品定位、用户流程和前端责任边界。
3. 已有实现不能反过来决定“用户应该看到六个页签”。
4. 技术字段和安全按钮不能抢占主叙事。
5. 在新基线重新验收前，历史 `PASS` 只能是历史记录。

因此当前正确顺序是：

```text
双命题证据
→ 产品发现与最小策略
→ PRD/范围/用户流程/前端
→ 决策与风险
→ 文档冻结
→ 重新审计已有原型
→ 最小修正
→ 独立验收与提交
```
